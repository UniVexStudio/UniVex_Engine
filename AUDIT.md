## 2. Paano ginawa ang audit

1. **Structural inventory** — per-module file/line counts, target names, and dependency edges (parsed mula sa `#include` graph ng lahat ng 774 source files).
2. **Compile audit** — bawat isa sa 236 engine `.cpp` + 368 engine `.h` + 170 test `.cpp` ay dinaan sa `g++ -std=c++20 -fsyntax-only` gamit ang eksaktong defines ng build system (`UVE_HAS_STD_FORMAT=0`, profile defines mula sa `UveBuildConfiguration.cmake`).
3. **Duplicate detection** — three layers: (a) MD5 exact-file duplicates, (b) 20-line rolling-window exact-match sa lahat ng files, (c) name-stripped structural (fuzzy) similarity scan sa 603 files, cross-module.
4. **Dead-code / wiring audit** — bawat `.cpp` sa disk chinek kung naka-declare sa CMakeLists (at kabaliktaran); bawat module chinek kung may external consumer.
5. **Fix verification** — ang iisang compile break ay sinubukan kung nagpo-compile pagkatapos ng proposed 1-line fix (pumasa).

## 4. 🔴 SIRA (broken) — detalyado

### 4.1 P0 — CONFIRMED build break: `wav_metadata_uve.cpp`

**File:** `Engine/Runtime/Audio/Internal/wav_metadata_uve.cpp`
**Error:** `'to_integer' is not a member of 'std'` (lines 13, 18-21 and onward)

```cpp
#include <cmath>
#include <cstring>
#include <limits>          // ← std::to_integer() lives in <cstddef>; hindi ito kasama
```

- Ginagamit ang `std::to_integer<T>(bytes[i])` pero walang `#include <cstddef>` sa cpp **ni** sa header nito (`wav_metadata_uve.h` — may `<cstdint>`, `<optional>`, `<vector>` lang).
- Sa GCC-12/libstdc++ 12 (na ginagamit ng inyong hosted Linux per `UveBuildConfiguration.cmake` comment) **100% hindi ito magko-compile** — hindi ito lint warning, paos ang target na `uve_audio`, at lahat ng umuugat dito (`uve_core`, `uve_editor_app`, tests).
- Ironic: 5 **ibang** audio headers sa same module ay tamang nag-iinclude ng `<cstddef>`.
- **Fix (verified compiles clean):**
  ```cpp
  // Engine/Runtime/Audio/Internal/wav_metadata_uve.cpp, after line 7:
  #include <cstddef>
  ```
- Bonus check: ang `Test/Audio/` — walang `wav_metadata_uve_tests.cpp`. kaya hindi ito nahuli. Ang Audio tests na mayroon (`wav_pcm16_decoder`, `audio_*`) ay hindi tumatama sa broken file. **Kulang ang test coverage sa mismong file na sira.**

## 5. 🔴 DUPLICATES — detalyado

### 5.1 Parametric clone family #1: Asset importer pipeline (pinakamalaki)

**Ganito ang pattern:** parehong par 106-line functions, 100% structurally identical kapag tinanggal ang pangalan na nag-iiba. Literally same control flow, same error messages shape, different lang ang asset type at extension string.

| Clone pair / family | Similarity | Linya | Files |
|---|---|---|---|
| `obj_importer_uve.cpp` ≡ `mtl_importer_uve.cpp` | **100%** | 106×2 | OBJ vs MTL — magkaibang domain, iisang skeleton |
| `bmp_importer_uve.cpp` ≡ `tga_importer_uve.cpp` | **100%** | 106×2 | BMP vs TGA |
| png/jpeg vs bmp/tga pairs | ~62–67% | 118×2 vs 106×2 | 4-way partial clone |
| **Lahat ng 8 importer headers** (obj/mtl/bmp/tga/png/jpeg/gltf/shader_source) | **100%** | ~16 each | Same class shape, ibang pangalan lang |

**Implikasyon:** ~950 linya ng near-identical code. Kapag nagbago ang import policy (e.g. bagong size cap, bagong atomic-save behavior), kailangan ng edit sa **9 na lugar** — classic copy-paste drift trap. Sa anumang "AAA" standard, ito ay isang template/helper na `ImporterSkeleton<AssetT, Converter>(maxBytes, extension, saveFn)` plus per-format converters (na siya nang totoong format-specific logic sa `*_converter_uve.cpp` at `*_metadata_uve.cpp`, na **hindi** duplicated — maganda ang split na 'yon).

**Rekomendasyon:** P1 — gawing shared skeleton; iwanang per-format ang converters/metadata (malinis na ang mga iyon).

### 5.2 Clone family #2: RHI handle headers ×4

`buffer_handle_uve.h` / `texture_handle_uve.h` / `pipeline_handle_uve.h` / `shader_handle_uve.h` — **100% identical structure** (~37 lines each, ~150 total). ## 6. 🟠 SEMANTIC DUPLICATES & architecture risks

### 6.1 Dalawang math libraries (pinakadelikado)

| | Viewport mini-math | Core/Math |
|---|---|---|
| Files | `univex/math/Mat4.h`(72 ln) + `Mat4.cpp`(119) + `Vec.h`(80) | 10 headers + lib (≈ full kit) |
| Namespace | `univex::math` | `UVE::Math` |
| Layout | **Column-major** (GL direct) | **Row-major** |
| Clip space | **OpenGL [-w, w] z** | **Vulkan [0,1] depth** |
| Inverse | General 4×4 inverse ✓ | Wala (deliberate, per doc) |
| Used by | Viewport, EditorApp, App/editor | Lahat ng buong engine |

**Eto ang pinaka-alarming na finding sa audit na ito:** ang `Matrix4x4UVE::PerspectiveUVE` at ang `Mat4::Perspective` ay parehong "right-handed perspective", pero **magkaiba ang z-range at memory layout**. Kung may darating na tao na magpasa ng `Matrix4x4UVE` sa Viewport path (o mag-mix ng projection mula sa dalawa), makakakuha siya ng subtle depth/layout corruption na hindi makikita ng compiler. Sa ngayon, ang boundary ay disiplinado — verified na `EditorMeshLayer.cpp` lang ang may `uve/math` sa Viewport, at `App/editor/main.cpp` + `EditorApp/main.cpp` lang ang may `univex::math` sa labas — **pero boundary discipline lang ang pumipigil sa bug, hindi ang compiler.**

**Rekomendasyon (P1):** long-term, i-unify sa `UVE::Math` (idagdag ang general inverse + column-major view adapter), o kaya i-gawing hard wall: i-rename ang Viewport math bilang `glmath`/`viewport_gl` namespace na may `ToUveMath()` / `FromUveMath()` explicit conversion functions sa iisang header, at i-ban ang `univex::math` sa labas ng Viewport via CI grep.

### 6.2 Include-prefix collisions (trap, hindi active bug) — **RESOLVED 2026-09-17**

Lima ang modules na nag-eexpose sa shared prefix na `uve/core/`: **Animation** (`animation_clip_uve.h` atbp.), **Core/Diagnostics**, **Core/Scheduling**, **Engine**, at **Object**. Ngayon, walang filename collisions (verified) — pero isang araw may gagawa ng `uve/core/event.h` sa dalawang module at silent header shadowing ang mangyayari. Gayundin ang `uve/scene/` na pinagsasaluhan ng **Component, Entity, at Scene** modules, at `uve/render/` na pinagsasaluhan ng **5 RHI modules**.

**Resolution (naitala sa follow-up log, #§6.2):** bawat exposed prefix ay may iisang owner module na ngayon. Rule: **include prefix = target suffix** (`uve_<name>` ⇒ `uve/<name>/`): `uve/animation/`, `uve/diagnostics/`, `uve/scheduling/`, `uve/object/`, `uve/component/`, `uve/entity/`, `uve/rhi/`, `uve/rhi_null/`, `uve/rhi_opengl/`, `uve/render_systems/`, `uve/rhi_shader/`. Ang **Engine** (`uve_core`) ang nag-iisang owner ng `uve/core/` — tugma ito sa reference-engine layout (`engine/core/`, ayon mismo sa Animation CMakeLists comment) kaysa gawan pa ng bagong prefix. Ang `uve/render/` ay buong na-retire.

### 6.3 Overlapping scene/entity/node triple

Tatlong lugar ang may say sa "ano ang node/entity": `Component` (25 headers ng components), `Entity` (ECS: chunk/archetype/entity_manager), at `Scene` (`scene_node`, registry, graph). Ang disenyo ay functional (verified ang edges), at ang `Nodes/3D` ay node *types* sa ibabaw nito — hindi ito duplication, pero **mahalagang maidokumento ang ECS↔SceneNode boundary** kung papunta sa AAA, kasi ito ang unang lugar na nagkakagulo sa mga ganitong laki ng engine.

- **2026-09-19 (§1.2 — the ECS walk itself: 535us to 31us, and it was never a rendering fix):** Having cached placements, the remaining extraction cost was the walk, so I read `EntityManagerUVE::ForEachErased` before assuming anything. - **2026-09-19 (§1.2 — caching placements, after measurement said the obvious answer was wrong):** The natural next step after splitting extraction was a BVH, and I wrote a benchmark against the engine's own maths before building one - which killed the idea. At 1000 entities, placement (quaternion normalize, TRS compose, AABB transform) costs ~153 us per frame while all four frustum culls together cost ~48 us; at 10000 it is ~1439 us against ~872 us. **Placement dominates, and a BVH only accelerates the cull.** Making all four culls instantaneous at 10000 entities would take the frame from ~2311 us to ~1439 us - less than half - while the dominant term sat untouched. So the honest win was not culling faster but not recomputing what had not changed, and a second benchmark put that at **~29x**: 139 us to recompute 1000 placements versus 4.8 us to compare keys and reuse them. Most objects in most scenes do not move in a given frame, so most of that 139 us was recomputing the previous frame's answer. Placements are now cached per entity in the visibility set. **The key is the transform PLUS the mesh guid PLUS the mesh's local bounds**, not the transform alone: a mesh that finishes streaming or is hot-reloaded keeps its transform while its bounds change completely, and a transform-only key would pin that object to whatever placeholder bounds it had when first seen. There are separate tests for a swapped mesh at an identical transform and for rotation and scale, because position is the obvious field to key on and the other two change world bounds just as much while being easy to forget. **Comparison is exact float equality, deliberately.** This is an identity test, not a tolerance test - a cache that rounds is a cache that drifts, and the drift accumulates invisibly, so a sub-millimetre nudge must miss. There is a test for exactly that. NaN falls out correctly for free: a NaN component compares unequal to itself, so a broken transform misses every frame and is recomputed every frame, which is right twice over, since recomputation is what rejects it and a cache "matching" two NaNs would be asserting that a broken transform is unchanged. **Keyed by EntityUVE, which is generational**, so a destroyed entity whose index gets recycled cannot inherit the dead entity's bounds. **Bounded by a frame stamp**: entries not touched during the walk are pruned, because without that a cache in a streaming world is a leak wearing a cache's clothes - there is a test that destroys an entity and asserts its entry disappears, and another that runs fifty frames and asserts the cache reaches a fixed size with zero misses. The stamp is written on hits as well as misses, since it records "seen this frame"; stamping only misses would evict every stationary object, which is precisely the set the cache exists for. Pre-incremented per build so 0 can mean "never populated", which is how the default entry that operator[] just inserted is told apart from a genuine hit. **Hit and miss counts are surfaced in Renderer3DFrameDiagnosticsUVE**, because a cache whose hit rate nobody can see is a cache nobody can tell is broken - a key bug that misses every single frame costs an extra comparison on top of the original work and otherwise looks identical to a working one. **Proof (+10 tests, run not merely compiled):** all-hits on the second build of a static scene, a hit producing a placement byte-identical to a fresh recompute, a moved entity recomputed with bounds that actually reflect the new position (the stale-placement bug is silent - the object simply renders where it was last frame), a 0.0001-unit nudge still missing, rotation and scale each independently invalidating with the scaled bounds verified to have genuinely grown, a swapped mesh guid invalidating at an unchanged transform, a destroyed entity pruned, fifty frames not growing, the cached path producing the identical queue to the uncached one, and an end-to-end renderer test asserting the second RenderFrameUVE reports hits - that last one matters because the renderer owns the set across frames, and a set rebuilt per frame would silently never hit while every unit test still passed.

- **2026-09-19 (§1.2 — cached offscreen target sets: fixing the viewport cost that was actually real):** Asked to continue "basta makakabuti sa viewport at engine", I checked whether the obvious next step - wiring CS8's indirect draw into the instanced path - would actually qualify, and concluded it would NOT at the engine's current scale, so I did not build it. CS8 wins on thousands of instances of one mesh - a forest or a crowd - which this engine does not yet have. (2) Worse, culling currently happens during EXTRACTION, where the same pass computes each item's worldBounds and derives `sortDepth` from it. Moving the cull to the GPU does not remove that work: the CPU still needs bounds to depth-sort, so it would compute them anyway and the GPU would then redo the identical test. - **2026-09-18 (§8 #2 — CS10 "GPU skinning": the precision question had to be answered before the kernel was written):** With CS9's data model and CPU authority in place the kernel itself was straightforward; the slice's real content was a recon finding that arrived before a line of GLSL was written. **`Math::TransformPointUVE` accumulates in double.** GLSL has no portable float64 - it is an optional Vulkan feature absent from whole classes of hardware - so a GPU kernel cannot reproduce that. I measured the consequence rather than guessing at it: ~16% of vertices land on a different float, with the error bounded at 2.3e-7 relative to term magnitude (about 2x float epsilon). Small, but NOT bit-for-bit, and `precise` cannot fix it because the discrepancy is the accumulation type, not FMA contraction. Every previous workload (CS4, CS5, CS8) reached bit-for-bit because its CPU counterpart was pure float - `PlaneUVE::GetSignedDistanceUVE` is float-first with a double fallback only for non-finite input, and the particle integrator is plain float. Skinning was the first one where that was not true. **Three honest options existed and the choice matters more than the kernel does.** A tolerance-based test was rejected: the moment "close enough" is accepted, a genuinely wrong weight also looks like a small error, and the ability to detect it is gone permanently. `shaderFloat64` was rejected: an optional feature absent from GLES-class hardware, which would have made the entire workload conditional to buy one ULP. What shipped instead is a float-accumulating transform LOCAL TO THE SKINNING MODULE (`TransformPointFloatUVE`), leaving `Math::TransformPointUVE` untouched for the camera and general-purpose callers where double is the right answer. That also fixed a defect CS9 had already shipped without noticing: its `TransformDirectionUVE` was float while its position path was double, so a single vertex was being transformed by two different arithmetics under the same matrix. The precision given up is ~1e-7 relative on model-space positions - nothing - and what is bought is exact CPU/GPU agreement, which means the CPU fallback is not merely "similar" but identical, with no popping when a caller switches paths. **The kernel:** blends matrices then transforms once (algebraically identical to transforming per joint and blending, numerically not - so the choice is stated in both implementations); skips zero-weight slots rather than multiplying, since an unused slot may hold any joint index and 0 times infinity is NaN; and carries `precise` on the BLEND ACCUMULATOR as well as the final transform, because each `acc += M * w` is itself a contractible multiply-add and qualifying only the transform would leave the subtler half of the hazard open - asserted in the portability test. The dot products are spelled out element by element rather than as `blended * vec4(p, 1.0)`, because `precise` can only constrain operations the shader names and a matrix-vector product leaves the accumulation order to the compiler. **Pose resolution deliberately stays on the CPU:** walking a parent chain over a handful of joints is serial work a dispatch cannot accelerate, and keeping `TryResolvePoseUVE` the single authority means one implementation to be correct. Matrices are transposed on upload (row-major `Matrix4x4UVE` into std430's column-major mat4), and that is the failure this kernel is most exposed to because it is QUIET - a symmetric pose produces plausible output either way. So a test uses a pure translation, whose transpose would hide the translation in a row nothing reads and leave vertices unmoved. **Proof (+11 tests):** bit-exact comparison via memcmp of the float bits, deliberately not `EXPECT_FLOAT_EQ` whose 4 ULP tolerance is precisely the size of the discrepancy this design eliminated; 1000 vertices on an awkward animated pose against the CPU on both GL and Vulkan; the bind pose returning source vertices unchanged; the transpose test; partial workgroups (1, 63, 64, 65, 129) each run twice to catch a reused output buffer left dirty; unnormalized input normals so a stray `normalize()` on either side shows immediately; and the refusal set mirrored from the CPU path so a caller can switch between them without changing its error handling. - **2026-09-18 (§8 #2 — CS9 "skinning, unblocked": the data model and the CPU baseline, before any kernel):** The ROADMAP listed skinning as blocked, and the block was real but easy to misread. Weights are stored AS AUTHORED and never silently renormalized - a weight set that does not sum to one is an asset defect, and quietly fixing it would hide it from the importer that could correct it at the source; `IsSkinningInfluenceNormalizedUVE` is how a caller detects it instead. `inverseBindMatrix` is stored rather than derived, because deriving it means inverting the bind pose at load time and a float inverse is not bit-identical to the exporter's - which would put a silent discrepancy between exactly the two paths this data exists to keep in agreement. An out-of-range joint index is rejected EVEN AT ZERO WEIGHT, because a GPU path indexing a joint array with it reads out of bounds regardless of what it then multiplies by. **The serialization decision worth recording:** the skinning data is an OPTIONAL section trailing the existing payload, so a static mesh writes byte-identical output to what previous versions produced and a file that simply ends after the bounds is a static mesh rather than an error. - **2026-09-18 (§8 #2 — CS8 "indirect cull": the culling answer stops coming back to the CPU):** CS5 culls on the GPU and hands the answer back; CS7 added a draw whose parameters live in device memory. CS8 is the pass that joins them, and the design question it answers is what the GPU should WRITE. A visibility array per box — CS5's output — would still need the CPU to scan it, count survivors, and issue draws, which is the round trip the whole exercise is meant to delete. So the kernel writes the two things a draw actually consumes: the `instanceCount` word of a `DrawIndexedIndirectCommandUVE`, and a COMPACTED buffer of surviving box indices for the vertex shader to index with `gl_InstanceID`. A single `atomicAdd` does both jobs at once — it accumulates the count and hands each surviving invocation a unique compaction slot — which is why the draw-command block is the one SSBO in the kernel that is NOT `writeonly`: an atomic reads as well as writes, and the tidier-looking qualifier would make the kernel's one essential operation illegal. That is asserted in the portability test rather than left as a comment. **The consequences of the atomic are load-bearing and documented on the class.** Slot assignment has no ordering, so the compacted list is a SET, not a sequence: draw order is not stable frame to frame, which is fine for the opaque geometry an indirect cull pass is for and wrong for anything depending on submission order. Every test therefore sorts before comparing; one that asserted an order would fail intermittently for a reason that is not a bug. And because the atomic stores without a bounds check, the index buffer is allocated at one slot per box — the worst case is everything visible — which `EnsureBufferCapacityUVE` states explicitly, since shrinking it to an expected-survivor estimate would turn a full frustum into an out-of-bounds write. **The seed step:** the host writes the four MESH fields (indexCount, firstIndex, vertexOffset, firstInstance — none of which a culling decision can change) and forces instanceCount to zero regardless of what the caller passed, because the kernel only ever ADDS to that field. A run that forgot to re-zero would report twice the survivors on the second call and every call after, and nothing downstream would notice, because in production that number never reaches the CPU. That is precisely why it has its own test on both backends. An empty box list still writes the zero-instance command, so a caller that unconditionally records an indirect draw gets a well-formed no-op rather than last frame's parameters. **Verification is the interesting part, since the system's whole value is that it does not report its result.** The tests read the buffers back afterwards purely as observers — `PrepareUVE()` performs no readback and the diagnostics expose no visible count, so no production path can come to depend on one; a test asserts that field list directly. - **2026-09-18 (§8 #2 — CS7 "indirect draw": the parameters of a draw can now come from the GPU):** CS5 shipped GPU frustum culling and CS6 made it actually run on both backends, but the result still had to come back to the CPU before anything could be drawn with it — which is the one thing a culling pass exists to avoid. The RHI simply had no draw whose counts live in device memory. CS7 adds `ICommandBufferUVE::DrawIndexedIndirectUVE(buffer, offsetBytes)` and the resource type it needs. **The design decision worth recording is the usage.** A first instinct is a plain `Indirect` usage; that would have been useless. An indirect buffer the compute stage cannot bind as an SSBO can only be filled by the CPU, and a CPU that knows the counts can simply call `DrawIndexedUVE`. So the new enumerator is `BufferUsageUVE::IndirectStorage` and it is both things at once — `VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT | VK_BUFFER_USAGE_STORAGE_BUFFER_BIT` on Vulkan, and on GL it keeps `GL_SHADER_STORAGE_BUFFER` as its home target with `GL_DRAW_INDIRECT_BUFFER` used only as a transient draw-time bind (GL buffer objects are untyped; a "target" is a binding slot, not a property of the object). Because the home target can no longer distinguish it from a plain `Storage` buffer, the GL buffer record now carries the usage explicitly rather than inferring it. The two places that asked "is this bindable as storage?" — Vulkan's replay-time storage-bind check and GL's compute-support gate — went through a new `IsStorageBindableUsageUVE(usage)` helper instead of growing a second hardcoded comparison each. **The parameter block:** `DrawIndexedIndirectCommandUVE` is a five-word POD, `sizeof == 20` asserted, matching `VkDrawIndexedIndirectCommand` and GL's `DrawElementsIndirectCommand` field for field — including `vertexOffset` being the one SIGNED member, since an unsigned mirror would turn a small negative rebase into a four-billion vertex index. That struct is what a compute kernel writes through std430 and what both backends hand the driver, so a silent reorder would produce draws with nonsense counts that, by the nature of indirect draw, nothing on the CPU would ever observe. That invisibility is also why both real backends VALIDATE rather than trust: the offset must leave a whole command inside the buffer, the handle must be live, the usage must be `IndirectStorage`, and a compute pipeline must not be bound — each a warn-and-skip rather than a garbage draw. GL additionally issues `GL_COMMAND_BARRIER_BIT` before the call (the barrier bit that specifically orders shader writes against indirect-parameter fetches — a storage barrier does not cover this) and unbinds `GL_DRAW_INDIRECT_BUFFER` afterwards so no stale binding can feed the next draw. **All four `ICommandBufferUVE` implementers were updated in the same breath, the services-test fake included** — the M2f lesson, now routine: grep for every `override` of a sibling method before adding a pure virtual, not after the build breaks. - **2026-09-18 (§8 #2 — CS6 "the workloads were GL-only": SPIR-V for the built-in compute kernels):** Recon for the next workload turned up something worse than a missing feature - a shipped one that did not work where it claimed to. CS4's particle simulation and CS5's culling were both written as backend-independent engine systems taking any `IRenderDeviceUVE`, and both were proven on a real GL context. But their kernels existed only as GLSL text, and the RHI takes each backend's OWN shader language (GLSL on OpenGL, SPIR-V bytes on Vulkan - runtime translation remains an open ROADMAP item with no toolchain in this build). On Vulkan `InitializeUVE()` therefore returned false and the workloads silently fell back to nothing: a capability gap wearing the shape of a working feature, and exactly the kind of thing that stays hidden because the only tests exercising it ran on the backend where it worked. **Two defects, not one.** Rebuilding the sandbox shader toolchain (cmake/ninja via venv, glslang @ vulkan-sdk-1.4.321.0 from source - apt remains unreachable here) and pointing it at the kernels produced an immediate hard error on both: `'uDeltaSeconds' : non-opaque uniform variables need a layout(location=L)`. SPIR-V has no non-opaque global uniforms at all, so the convenient GLSL form the GL backend resolves by name can NEVER compile for Vulkan - the kernels were not merely un-baked, they were unbakeable as written. Both now pass their parameters in std430 storage blocks (`ParticleSimulateParams` at binding 1, `FrustumCullParams` at binding 3), which compiles unchanged for both backends; the hosts upload a small fixed-size parameter record allocated once at initialization rather than writing named uniforms. With that fixed, both kernels were baked to SPIR-V in `built_in_compute_spirv_uve.h` beside the GLSL they came from (byte-array form with a sizeof-derived length, because SPIR-V's first NUL byte falls at offset 4 and a cstring construction would truncate 4720 bytes to 4 - the M2a defect, in the one place it still applies), and a shared `SelectKernelSourceUVE()` picks the payload the injected backend can consume. **Proof (+7 tests):** four portability tests guard the properties a reader would otherwise have to take on trust - the baked modules are word-aligned with the right magic and a non-zero id bound; the engine's own length-explicit string construction preserves every byte while a cstring construction demonstrably does not (asserted, so the NUL guard cannot silently stop guarding); no kernel contains a bare `uniform` outside a `layout` block or a comment, which is the exact construct that made them Vulkan-incompatible; every binding index the kernels declare matches what the hosts bind, since a mismatch there is invisible at compile time on both backends and simply produces wrong numbers; and `precise` is still present, since losing it would quietly downgrade CS4/CS5's exact guarantee to an approximate one without failing to build. Three more run the ACTUAL workloads against a real headless Vulkan device (VK_EXT_headless_surface, skipping only when no ICD provides it): the particle simulation over 1000 particles matching `ParticleRuntimeUVE` element for element, the cull over 1000 boxes matching `FrustumUVE::IntersectsUVE` on every one, and the thirty boundary boxes placed exactly on each plane and nudged one ULP either way - the same bit-for-bit standard on the second backend, which is the only thing that actually demonstrates the systems are backend-independent. `uve_integration_tests` gained the Vulkan backend in its link list for this (the Vulkan device tests live in `uve_core_tests`, which does not link the render systems, so the new file had to go where the systems are). Local per-TU syntax verification clean on all touched TUs pre-push, embedded-vs-file shader parity re-checked byte-wise after the kernel edits; CI is the arbiter of green.

- **2026-09-18 (§8 #2 — CS6 fix-forward: the two backends do not submit at the same time):** CS6's Vulkan arms went red on their first CI run, and the cause was a genuine backend-model difference the GL-only proofs could never have exposed. `GlRenderDeviceUVE` executes every command at RECORD time - its `SubmitUVE()` does nothing but release the buffer - so `ParticleComputeSimulationUVE` and `FrustumCullComputeUVE` reading their storage buffers immediately after submitting saw finished work. `VulkanRenderDeviceUVE` queues the recording into `frameSubmissions` and replays it in `PresentUVE()`; until that runs, the dispatch has not touched the GPU, so the readback returned PRE-dispatch contents. Both systems now call a documented `FlushComputeSubmissionUVE()` (a `PresentUVE()` with the reasoning attached) between submission and readback - a no-op cost on GL, the actual execution point on Vulkan - and both headers state the consequence plainly, since presenting the device is a side effect a caller needs to know about and means these are steps to run outside the render frame's own present. Worth recording as a lesson rather than a typo: CS4 and CS5 both claimed to be backend-independent on the strength of passing against one backend, and the claim was wrong in two separate ways (GLSL-only kernels, then this) - "works on the backend we tested" is not the same as "is backend-independent", and only running the second backend found either. **CI forensics reordered in the same commit:** the improved block from CS4 correctly named all three failing tests this time, but led with ctest's summary and the failing-test NAMES and exhausted GitHub's ~10-annotation cap before emitting a single `Value of:` line. The names are the cheapest information to recover; the assertion bodies are the part that cannot be reconstructed from anywhere else when the log CDN is unreachable. Bodies now come first and every section is individually capped.
